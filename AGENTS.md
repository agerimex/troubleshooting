# AGENTS.md

This file provides guidance to AI coding agents (Codex, Claude Code and others) when working with code in this repository. `CLAUDE.md` only imports this file, so edit this one.

## Overview

Troubleshooting is an MVP observability system: Go services send OpenTelemetry traces and correlated log records over gRPC into ClickHouse, and a Vue 3 UI explores traces with their logs in one table (Log Analysis), investigates one execution as Timeline or Sequence with its logs, groups recurring problems, and compares call statistics, latency percentiles and error groups between releases. The acceptance scope is `features/milestone_1/*.feature` and `features/milestone_2/*.feature` (Gherkin, with `METRIC_CONTRACT.md` and `REFERENCE_FIXTURE.md`); `docs/milestone1-completion.md` and `docs/milestone2-completion.md` map each scenario to its checks. The problem workspace (an added page, from `troubleshooting-ui-agent/`) is recorded in `docs/problem-workspace.md`, and its Sequence variant (from `Troubleshooting_Sequence_Agent_Package.zip`) in `docs/sequence-investigation.md`. The UI's navigation follows the product blueprint (`Troubleshooting_Product_Blueprint.zip`): `docs/product-blueprint.md`; Timeline & Sequence opens on the sequence library of execution shapes: `docs/sequence-library.md`. It is a monorepo of **independent Go modules** (no `go.work` is committed — it's in `.gitignore`) plus one npm project.

## Commands

Full stack (Docker):
```
make all              # builds docker-log-analysis:1, docker-log-ui:1, docker-log-receiver:1 and creates the external `troubleshooting_network`
make up               # docker compose up -d --wait: clickhouse + services; UI at http://localhost:8095
```
`make all` only builds the images and creates the network (idempotent); `make up` starts the stack. ClickHouse data lives in the named volume `troubleshooting_clickhouse-data`.

Tests:
```
make test             # Go unit tests of all modules + UI type-check and vitest
make ui-e2e           # Playwright checks of the UI against a mocked API (log-ui/e2e/*.e2e.ts)
make test-stack-up && make fixture-load && make fixture-check   # regression fixture, see fixtures/regression/README.md
make test-stack-reset # deletes only the isolated test stack (project troubleshooting-test) and its volume
```
The test stack (`docker-compose.test.yml`) uses its own ports (API 28094, OTLP 24317, …) and volume; never point fixture commands at the dev stack. On Docker Desktop a first ClickHouse start on an empty volume can take several minutes.

Go modules (run from inside each module directory):
```
cd log-receiver && go build ./cmd/grpc_api
cd log-analysis && go build ./cmd/rest_api
go test ./...                                  # in any module (protos and fixtures/regression too)
go test ./internal/data -run TestValidate      # a single test
```
Go tests are unit tests only (no ClickHouse needed); integration checks are the regression fixture. On Windows, `gofmt -l` lists every file because git checks them out with CRLF; pipe through `tr -d '\r'` to check real formatting.

UI (`log-ui/`):
```
npm install
npm run dev           # vite dev server; talks to the API at VITE_LOGS_APP_API_URL from .env (http://localhost:8094)
npm run build         # vue-tsc type-check + production build in parallel
npm run type-check
npm run test:unit     # vitest: src/**/__tests__
npm run test:e2e      # Playwright (needs Node 20+; npx playwright install chromium once)
```
The lockfile is committed; Docker and CI use `npm ci`.

Regenerating protobuf code (`protos/logs/*.pb.go`) — needs a local clone of `open-telemetry/opentelemetry-proto` on the include path (see `protos/README.md`):
```
cd protos
protoc -I<path-to>/opentelemetry-proto -I. --go_out=. --go-grpc_out=. logs.proto
```

## Architecture

Data flow:
```
instrumented Go app ── log-sender (spans + logs) ────gRPC :50055──▶ log-receiver ──▶ ClickHouse (otel_traces, log_records)
any OTel SDK / Collector ─────────── OTLP/gRPC :4317 ──────────────────▲                  ▲
browser ── Caddy :8095 (log-ui static /dist) ── /api/* ──▶ log-analysis :8094 (chi REST) ─┘
```

- **protos/** — `logs.proto` defines `LogService` (`LogMessage`, `SendSpans`, `SendLogs`) and a flattened `OneSpan` message. `LogMessageRequest` fields 3–8 (`record_id`, `trace_id`, `span_id`, `severity`, `service_name`, `attributes`) are optional, so old senders that set only message and timestamp keep working. Regenerating needs `google/protobuf/timestamp.proto` on the include path. Module `github.com/agerimex/troubleshooting/protos`.
- **log-sender/** — library imported by client apps (module `github.com/agerimex/troubleshooting/log-sender`). `NewTracer(svcName, opts...)` installs a global OTel `TracerProvider` with a batch processor and a `CustomExporter` (one long-lived gRPC connection) that converts `ReadOnlySpan`s to `pb.OneSpan` (`spanToProto`) and calls `SendSpans`; `Shutdown(ctx)` flushes it. Address: `WithAddress` > the legacy `addrTrace` flag (read once in `NewTracer`; the library must never call `flag.Parse`). Token: `WithToken` > `TROUBLESHOOTING_TOKEN`. Export errors are returned to the span processor — the library must never exit or panic in the host app. `Duration` is sent in **microseconds**. Logs (`logs.go`): `NewLogExporter(svc, opts...)` + `Send(ctx, []LogRecord)` returns nil only after the receiver stored the records (retry the same records on error; `RecordID` makes the retry count once); `NewLogRecord(ctx, …)` takes trace/span from the active span; `NewLogWriter` is a zerolog `io.Writer` that buffers (10 000, oldest dropped and counted) and flushes in the background, keeping unconfirmed records; `TraceHook` adds `trace_id`, `span_id` (only for a valid span — an all-zero id is rejected by the receiver), `record_id` and `record_time`. `logger.go` keeps the old public types (`ClickHouseWriter` etc., deprecated). `WithResourceAttributes` adds `service.version`, `deployment.environment.name` etc. (constants `Attr*`) to the resource of spans and to every log record.
- **log-receiver/** (module `log-receiver`) — gRPC server on `LISTEN_ADDR` (`:50055`). On startup it runs `CREATE TABLE IF NOT EXISTS` for `otel_traces` and `log_records` (`internal/driver/clickhouse.go`), so the **schema lives here**. The old `logs` table is no longer created or written (an existing one expires through its TTL). Spans are inserted per request; the column order in `InsertTraceData` must match the table definition exactly, and the `Events.*` / `Links.*` arrays must have equal lengths (ClickHouse Nested). Logs: `data.LogRecordFromProto` validates and normalizes a record (trace id 32 hex, span id 16 hex, neither all zeros; empty stays empty and is never inferred; severity upper-cased with aliases; a missing `record_id` gets a random one). `SendLogs` inserts the batch and answers after the insert (an invalid record rejects the whole batch: `InvalidArgument`; a failed insert: `Unavailable`). `LogMessage` goes through `internal/batch` (flush at 100 items or every second, drained on graceful shutdown), whose `Add` waits for the flush of its item and returns its error, so no record is confirmed before it is written. Retries store duplicate rows with the same `RecordId`; reads deduplicate. With `TROUBLESHOOTING_TOKEN` set, a unary interceptor (`cmd/grpc_api/auth.go`) requires `authorization: Bearer <token>`. The same gRPC server also serves the standard OTLP trace service on `OTLP_LISTEN_ADDR` (`:4317`; both ports serve both services, gzip accepted): `internal/otlp` converts OTLP spans to `pb.OneSpan` and reuses `InsertTraceData`. Spans with an invalid id (wrong length, all zeros, or a non-empty parent of the wrong length) are rejected and reported as partial success. Gotchas it handles: OTLP status codes are Ok=1/Error=2 (stored as Go API Error=1/Ok=2), an empty parent becomes `0000000000000000`, and OTLP has no child count (stored as 0). Schema and retention live in `internal/driver/schema.go` (`EnsureSchema`): it also creates `stat_calls`, `stat_errors`, `stat_shapes`, `stat_revisions`, `collection_heartbeats`, `coverage_declarations` and `analyses`, adds `ReceivedTime` (receiver time, 0 for older rows) to the raw tables, and applies `TRACE_RETENTION`/`LOG_RETENTION`/`STATS_RETENTION` to existing tables with `MODIFY TTL` only when they differ (`retention.go` rejects raw retention ≤ 1 h + `STATS_ALLOWED_LATENESS` + 1 h). Inserts name their columns (unquoted: the driver only strips backticks). A heartbeat row every 15 s marks collection coverage. `stat_errors` also has `Calls` (distinct `TraceId:SpanId` state) and `HasCalls` (0 in rows written before it existed, so their call counts are unknown, never 0); `detection_rules` (no TTL) stores every saved revision of the problem detection rules. An OTLP span without an end or ending before its start gets `Duration` -1 (`InvalidDuration`), never 0.
- **log-analysis/** (module `logs-backend`) — chi REST API on `LISTEN_ADDR` (`:8094`): `POST /api/v1/view-spans` (`{Spans, HasMore}`), `POST /api/v1/count-spans`, `POST /api/v1/search-logs` (`{Logs, HasMore}`), `POST /api/v1/trace-report` (`{Report}`). Log reads (`internal/data/logrecords.go`) mirror spans: `LogFilter.Validate`, `canonicalLogs` keeps one row per `RecordId` in the window before filters (a page uses `logPageCandidates` + `logPageCanonical` and the total `countByTime`, exactly as spans do), cursor `(UnixTime, RecordId)`, service/message are `positionCaseInsensitiveUTF8` substrings (no LIKE wildcards). `report.go`: `BuildReport` queries the spans section (via `selectSpans`, no child counts) and the logs section concurrently through `ReportSources` (replaceable in tests); each section has its own status (`ok`/`unavailable`/`limit`/`error`), `shown`/`limit`/`truncated`, and `total` (nil if the count failed), so the endpoint answers 200 even when a source fails; `retentionWarnings` uses the effective table TTLs (read by `LoadPolicy`). `sections` lets the UI retry one section. It instruments itself via log-sender (sends its own traces to `TRACE_RECEIVER_ADDR`). Span reads live in `internal/data/spans.go`: `SpanFilter.Validate` requires a half-open `[time_from, time_to)` window (≤ `MaxWindow`), validates hex ids, requires `trace_id` with `parent_id`, defaults `scope` (`root` without trace, `all` with one) and caps rows; invalid filters are 400 before any query. `conditions()` builds the WHERE parts with ClickHouse named params (only the ones used are bound). Every query reads from `canonicalSpans(conds)`: one row per (TraceId, SpanId) chosen by `winnerOrder` (error status, more events, more links, then `cityHash64` of the non-identity columns) among the span's rows in the window, **before** filters; the `IN` pre-selection only narrows work. Child counts (`fillChildSpanCounts`, per (TraceId, ParentSpanId), within the window) group the children's copies by start time (`childGroups`): copies that all name the same parent count without ranking; children whose copies disagree go through `canonicalSpans`. The total (`SelectCountSpans`) doesn't: a row whose start time no other row shares is its span's only row and counts if it matches (`timeGroups`, grouped only at the start times of matching rows); only rows at shared times are ranked per span with the winner tuple (`sharedTimeSpans`, the times passed as a list up to `maxSharedTimes`, else as a subquery). Replays don't change either. A page (`selectSpans`) does not canonicalize the rest of the window: `pageCandidates` reads the next `2×(rows+1)` matching rows with `ORDER BY "UnixTime" LIMIT n` (the sorting key alone and no `WITH TIES`, or ClickHouse reads everything instead of stopping early), then `pageCanonicalSpans` picks the winner among those spans' rows in [first candidate, last candidate time) — exact because retries/replays keep their start time; copies of one span with *different* start times aren't compared. A page that comes out short retries with 16× candidates, then falls back to `canonicalSpans`. Pages read `rows+1` to set `HasMore`. Every query carries `QueryLimits` settings (`limits.go`: `max_execution_time`, `max_rows_to_read`, `max_memory_usage`, overflow mode `throw`); `ExplainQueryError` maps limit/deadline errors to `ErrQueryLimit` → HTTP 504. A `requestDeadline` middleware bounds each request; handlers must pass `r.Context()` down (queries are traced as its child spans, `internal/data/tracing.go`). It reconstructs readable SQL for DB spans by substituting `db.sql.args.N` attributes into `db.statement` (`fillSQLArgs`), and `db.query.parameter.<name>` attributes into ClickHouse `{name:Type}` placeholders (`fillNamedParams`). clickhouse-go v2.13 only accepts strings for `{name:Type}` parameters, so arrays and tuples are passed as literals (`arrayLiteral`, `pairsLiteral`). `TestEveryPlaceholderIsBound` catches a placeholder without a parameter. Statistics (milestone 2): `population.go` (`Population`, dimension columns from attributes, `*string` = any/not recorded), `statsql.go` (SQL builders: `statSpans`/`statLogs` pick the canonical row among *eligible* rows with `argMaxIf` — eligible = `ReceivedTime` before the analysis cutoff and before bucket end + lateness; only rows at a time shared with another row are grouped (`sharedTimes`), a row alone at its time passes through, so memory doesn't grow with the hour's records (an hour of 4.3 M spans: ~200 MB); refresh queries get at least a 1-minute timeout (`refreshTimeout`); `rawCalls`, `groupedErrors`, occurrences per source kind, errors-v1 `messageRules` shared with Go tests, versioned by `MessageRulesVersion` in the definitions; a statistics query with a preselection groups just the preselected records in one pass), `plan.go` (per hour: committed revision or raw records or unavailable, never both; partial hours need raw records), `stats.go` (`ComputeStats`, merges stored and raw `quantilesTDigestIfState` states in one query), `errorgroups.go`, `compare.go` (comparison-v1 rules, pure, unit-tested), `analysis.go` (`Compare` stores the analysis JSON in `analyses`), `examples.go`, `refresher.go` (rebuilds completed buckets: insert rows under a new revision, then the `stat_revisions` commit marker; final buckets are never replaced; `contentHash` skips unchanged buckets; a cheap `rawFingerprint` (row count and latest receipt time) skips hashing a bucket whose raw rows did not change since this process last checked it), `statsconfig.go` (effective retention read from `system.tables`, `Clock` with a test offset, coverage from heartbeats and declarations). Payload hashes sort maps (`mapSort`): the receiver writes attribute maps in random order, so an exact retry would otherwise look like a conflict. Problem workspace (`troubleshooting-ui-agent/`): `problems.go` evaluates problems of one service and window on request (not stored) with the latest rules: error groups (`errorProblem`: qualified by distinct affected calls; groups whose records name no span are listed as "Call attribution unavailable"), slow calls (canonical raw spans above the rule duration; unavailable outside raw retention) and release regressions (only from stored comparisons with an eligible p95, `regressionProblems`; none → `Waiting`); `rules.go` (`DetectionRules`, revisions with optimistic concurrency: a save names the revision it edited, 409 otherwise). Endpoints: `stats/calls`, `stats/error-groups`, `stats/examples`, `compare`, `analyses`, `stats/rebuild`, `stats/status`, `coverage`, `retention`, `problems`, `problems/services`, `detection-rules` (GET, POST to save), `stats/shapes` (sequence library, `shapes.go`: shapes-v1 = entry operation + the set of distinct caller -> callee calls, computed per trace with array functions, stored per hour in `stat_shapes` under the bucket's revision; final revisions from before shapes get theirs added, outcome `extended`); with `TEST_CLOCK_CONTROL=1` also `admin/clock` and `admin/stats/fail-next`.
- **log-ui/** — Vue 3 + TypeScript + PrimeVue + Tailwind. Navigation (product blueprint, `docs/product-blueprint.md`): `App.vue` shows five pages in order — Log Analysis (`TracePage.vue`, default), Timeline & Sequence (`ExecutionsView.vue` + `ExecutionViewer.vue`), Problems (`problems/ProblemsView.vue`), Releases (`ReleasesView.vue`: `CompareView` + `StatisticsView`) and Settings (`SettingsView.vue`: `DetectionRules`, read-only retention). Pages stay mounted once visited (v-show), so returning restores their state; every page opens an execution through `openExecution(ExecutionTarget)` (trace, window, optional span/log/view, origin), and the viewer is re-mounted with a new `:key` per opened execution, so an old response can never reach a newer one. The URL hash names the page or the open execution (`#/executions?trace=&from=&to=&span=&log=&view=`, identifiers only; legacy `#/investigate` and `view=timing` accepted); `src/services/navigation.ts` holds the pure parts (pages, `parseRoute`, `investigationHash`, `initialView`: explicit > saved preference > Timeline, inline-log attachment `logsOfSpanId`/`unattachedLogs`, `executionRow`). Log Analysis is the span table: each traversal (refresh/filter change) resolves the From/To window once into `searchWindow`; paging, expansion and the count use that same window; cursor = last row's time, trace id, span id; Next is enabled from `HasMore`, not from the total; the total is counted once per traversal and shows "Total unavailable" on failure; filtering switches scope to "Any depth" unless the user picked a scope; `requestSeq` keeps a slow old response from overwriting a newer one. Expanding a span loads its children by (traceId, parentId) with `maxChildren` **and** the trace's logs (one `trace-report` per trace and traversal, cached), shown as inline log rows of exactly that `(TraceId, SpanId)` in time order; a loaded child gets an expand arrow only if it has child spans or logs of its own (list rows keep theirs until expanded, then lose it if empty); trace-level and unmatched logs form a group under the root span; notices/errors are rows under the node (`messageNode`). Filters select span metadata only, never log text. Row actions (Open timeline, Open sequence, Copy investigation link, details) come from one `ActionMenu.vue` opened by the row button, right-click or keyboard. `ExecutionsView` opens on the sequence library (`SequenceLibrary.vue`, `docs/sequence-library.md`): distinct execution shapes of a window from `stats/shapes`, ten per page, with executions, failed share, p50/p95/p99 and buttons that open a representative execution as a sequence; a "calls" expander reads one execution's calls on demand; trace id lookup sits under "Open one execution by trace id"; Back from an execution opened there returns to the library. `ExecutionViewer` shows one combined report: origin with return, scope, completeness, warnings, per-section Retry (`sections`), Regenerate, Widen, linked traces, Timeline (`problems/TraceTimeline.vue`) or Sequence (`problems/SequenceView.vue`, pure model `src/services/sequence.ts`, sequence-semantics-v1: participants = recorded services; a CLIENT with exactly one SERVER child of another service is one arrow, both spans selectable via the CLIENT/SERVER switch; end markers are span completions; at most 6 lanes and 80 marks per page), `problems/LogInspector.vue` (selected span or all trace logs, task lanes by `task.id`, log list), events/links (`SpanEvidenceDialog.vue`), link copy with a selectable fallback, HTML/JSON export (report plus the sequence presentation) and, for a comparison example, "Include in comparison export" (`App.vue` keeps included reports per analysis id). Spans carry `spanKind` (not `kind`, which the span tree uses for node types). Report logic is pure and unit-tested in `src/services/report.ts` (`association` follows the recorded SpanId only, `completeness`, `mergeSections`, `exportJson`, `exportHtml` — everything escaped, CSP without scripts); span tree/time helpers (node keys `traceId:spanId`, nanosecond strings via BigInt, `LogNodeData`) in `src/services/spanTree.ts`; problem logic (timeline, lanes, scopes, `validateRules`) in `src/services/problems.ts`; comparison logic and exports in `src/services/comparison.ts`. Problems: list for one service and window, `ProblemDetail` (counts, "Why was this flagged?", retained examples with Open timeline / Open sequence, unlinked examples inspectable without a trace, `ProblemCompare` with "Check fixed release"). Releases: `StatisticsView` (one population: rows per operation/kind/version, hourly series, error groups) and `CompareView` (baseline/candidate `PopulationForm`s, the stored analysis, examples via `ExamplesPanel.vue`, saved revisions, regenerate, HTML/JSON export); statistics windows use the exact selected end (whole hours stay whole buckets). `LogSearch.vue`, `ReportView.vue` and `problems/TraceGraph.vue` are no longer used (kept until the owner decides). API access goes through a service/impl indirection: `src/api/*.api.ts` (singleton wrappers) are initialized with `src/logs-api/*.impl.ts` (fetch implementations), which call `requestJSON` (`src/services/request.ts`): it always resolves to `[error, result]` and never throws. Built into a Caddy image; `Caddyfile` serves `/dist` and proxies `/api/*` to log-analysis (production `.env.production` uses empty, i.e. same-origin, API URLs). Optional basic auth is selected by `import auth_{$UI_AUTH:off}`; the UI must not send an `Authorization` header unless it has a real token, or it would override the browser's basic-auth credentials.
- **fixtures/regression/** (module `github.com/agerimex/troubleshooting/fixtures/regression`, `replace`s log-sender and protos) — the regression fixture: `dataset.go` generates RF01–RF16 and `m1.go` the milestone 1 scenarios (spans by OTLP, logs by `LogExporter`, record ids `fx<run>-<alias>`, with their checks) from a run id + base time (stored in `.state/fixture.json`, so replays are byte-identical), `checks.go` holds literal expected answers (never computed with the API's SQL), `parity.go` sends the same spans through log-sender and the OTel OTLP exporter. Run via the Makefile targets. `m2.go`/`m2checks.go` generate and check the milestone 2 reference releases (T = base hour − 8 h, outside the RF/M1 windows) and small cases; `pw.go` sends the problem workspace reference traces, `seq.go` the sequence package's CLIENT/SERVER trace (SEQ-REAL-001), and checks problem counts and rule saves (PW-*); `m2retention.go` (`-retention`) moves the API's test clock (+25 h finalizes, +4 days expires raw, +31 days expires statistics), restarts the API and recreates the receiver with other retention.

Key conventions spanning multiple components:
- **Span identity** is (TraceId, SpanId); span ids repeat across traces. Children are (TraceId, ParentSpanId) — never query or key by span id alone.
- **Root spans** are those with `ParentSpanId = "0000000000000000"` (`scope: root`). The UI loads children lazily with `trace_id` + `parent_id` of the expanded node.
- **Time window and cursor pagination**: every span, log and report request has a half-open `[time_from, time_to)` window (`windowCondition`; an empty window is a 400) (Int64 nanoseconds as strings; the UI uses BigInt). There's no offset: the cursor is `after_time`/`after_trace_id`/`after_span_id` of the last row, rows are ordered by `(UnixTime, TraceId, SpanId)`, and the window stays fixed while paging. Paging only moves forward and is exact only for data that doesn't change meanwhile.
- Status is sent as a string (`unset`/`error`/`ok`) and mapped to `StatusCode` 0/1/2 via `StatusCodeMap`.
- Raw tables keep 3 days by default, statistics 30 days (receiver env, `ttl_only_drop_parts`).
- `clickhouse/low-resources.xml` (mounted into the ClickHouse container) tunes ClickHouse for a small install (idle CPU from ~10% to under 1% of a core): it turns off the internal system logs except `query_log` and `error_log`, and stops threads that poll on short timers (`async_insert_threads`, the async logger).
- All configuration is environment variables with defaults matching docker-compose (table in README.md). Run a service outside Docker against the compose ClickHouse with `CLICKHOUSE_ADDR=localhost:19000`.
- Event/link attribute maps travel as one JSON-encoded `pb.Attribute` per event/link (documented in `logs.proto`), to avoid a proto change.

## Cross-module dependencies

log-analysis and log-receiver use the **local** `log-sender` and `protos` through `replace => ../...` directives in their `go.mod`, so changes to those modules take effect in the services immediately. Because of that, the Go Dockerfiles must be built with the **repository root** as context (`docker build -f log-analysis/Dockerfile .`, as the Makefile does); building from inside a module directory fails. If a service starts using another sibling module, add a `replace` and matching `COPY` lines in its Dockerfile. The root `.dockerignore` keeps `.git`, `node_modules` and `*.tar` out of the context.

External applications import `log-sender` from GitHub (the `replace` in `log-sender/go.mod` is ignored for them), so they only get changes once they're pushed and the application updates its dependency. Keep `log-sender`'s public API backward compatible. Module paths were renamed to the `agerimex` GitHub account — keep imports on `github.com/agerimex/troubleshooting/...`.
